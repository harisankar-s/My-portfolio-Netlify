# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Security

- Never read, open, or print the contents of `.env` while exploring or working in this codebase. It holds real API keys (`ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`). Use `.env.example` instead to see which variables exist — it only contains empty/placeholder values.

## Commands

- `npm start` — local dev server with live reload (`eleventy --serve --watch`)
- `npm run build` — production build into `_site/` (`eleventy`)
- `npm run new-post` — interactive scaffold (`scripts/new-post.js`) that creates `src/blog/posts/{slug}.md` with frontmatter pre-filled and an empty `src/images/posts/{slug}/` folder. Prefer this over hand-creating post files.
- `npm run list-posts` — lists every post in `src/blog/posts/` with its date and title (`scripts/list-posts.js`).
- `npm run delete-post` — interactive picker (`scripts/delete-post.js`) that deletes a post's `.md` file and its `src/images/posts/{slug}/` folder after confirmation; pass a slug directly to skip the picker (`npm run delete-post -- some-slug`).
- No test suite, linter, or framework build step. There is no "run a single test" — verification is visual via the dev server.
- `npm start` (`eleventy --serve`) does **not** run Netlify Functions, so the AskHari.ai chat widget will fail its `fetch` calls under it. Use `netlify dev` (Netlify CLI, e.g. `npx netlify-cli dev`) instead when working on the assistant — it proxies Eleventy and runs `netlify/functions/*` locally. Copy `.env.example` to `.env` first.

Node 18 is pinned for the Netlify build (`netlify.toml`). Eleventy and Luxon are the only `devDependencies`; there are no runtime `dependencies` — the AskHari.ai function uses Node 18's built-in `fetch` rather than adding an SDK.

### Domain split: the build's `/` and `/about/` are not the public homepages

There are **two** domains. BrainByte used to have its own subdomain; it was folded into the main domain (like charliehills.ai, one site), and "BrainByte" is now only the brand of the newsletter and products.

The Eleventy build itself always puts the blog listing at `/` and the portfolio at `/about/` — but in production these two paths are presented as two separate domains, via `netlify/edge-functions/domain-router.js`:

- **`harisankarsivankutty.in`** (+ `www`) — the hub, CV and exam prep domain. The edge function internally rewrites `/` to serve the `/home/` build output (the hub), and serves `/about/` (the CV), `/guides/*` (exam prep) and `/files/*` (guide PDFs) as built; `/home/` 301s to `/`. Any other path not in its allowlist (those plus static assets, `/api/*`, `/.netlify/*`) 301s to the blog subdomain, so blog content is never dual-indexed.
- **`blog.harisankarsivankutty.in`** — the blog domain, served as the build outputs it (blog listing at `/`, posts at `/blog/{slug}/`, `/tags/*`, `/ask/`, `/now/`, feed, sitemap). `/about/`, `/guides/*` and `/files/*` 301 to the apex and `/home/` to the apex root. "About" and "Exam prep" links on blog pages point at `{{ site.portfolioUrl }}/about/` and `{{ site.portfolioUrl }}/guides/`.
- **Old `brainbyte.harisankarsivankutty.in`** (and any `/brainbyte/*` path): 301s to the apex. `/guides/*` and `/files/*` keep their path; everything else goes to `/guides/`. Keep that domain attached in Netlify (or keep its DNS) so the redirects keep working for old links.

- **Products and the exam prep data** live in `src/_data/brainbyte.json` — `practice` (Claude practice packs on Topmate), `kits` (starter kits; `post` links a kit to the blog post it came from), `kitPromise`, `coaching`, `tracks` (guides still being written, shown as "More guides on the way"), `bytes` (original practice questions; the hub shows `bytes[0]`) — edit that, not the templates; flip `status` to `live` and set `url` when something launches. The blog is the main traffic source: the listing's "Learn with me" sidebar cards and in-feed band, the "Exam prep ↗" nav link on every blog page, and the end-of-post CTA in `article.njk` (the post's own starter kit, else the Claude exam prep for Claude/Certification posts, else the Claude packs for GenAI posts, else the starter kits) all link to the apex (`{{ site.portfolioUrl }}/guides/`, `/#kits`, `/#join`).

- **Exam prep guides** (free, after charliehills.ai/guides; on the apex at `/guides/`): content in `src/_data/guides.json` (one object per guide: pitch, stats, intro, `domains[].lessons[]` with `tests`, `rules`, `traps` as `[wrong, right]` pairs; code terms in backticks, rendered as `<code>` by the `ticks` filter). `src/_data/bbLiveGuides.js` keeps `status: "live"` ones. **Exam prep is grouped by exam:** `src/_data/exams.json` lists each Claude exam (code, name, facts, `guide` slug, `packExam` matching a `brainbyte.practice[].exam`); `_includes/exam-prep-card.njk` renders one exam with its study guide and practice pack side by side (the hub's light card style). It's used on the hub (`#exams`, which replaced the separate Guides and Practice sections), the `/guides/` library ("Exam prep and guides", `src/guides/index.njk`) and at the end of each guide ("The other Claude exams"); coming-soon tracks show below as "More guides on the way". A new exam = an `exams.json` entry + its guide in `guides.json` (+ a pack in `brainbyte.practice`). Guides live now: CCDV-F (`ccdv-f-exam-tips`, Claude Certified Developer, Foundations; 8 domains, meta-rules, no pack yet), CCAR-F (`ccar-f-exam-tips`, 5 domains, a `recurring` rules list) and CCAR-P (`ccar-p-exam-tips`, 7 domains, `intro.metaRules` instead, facts with a `sub` line); the template handles either shape, and `packExam` picks the matching Topmate practice pack. `src/guides/guide.njk` builds `/guides/{slug}/` with the `hub-page.njk` layout (the hub's sky, nav and footer via the shared `hub-nav.njk` / `hub-footer.njk` partials; styles in `src/assets/guides.css`): the header sits on the dark sky, the lessons on a white `.bg-paper` panel (pitch + "What's inside", intro and first lesson open, then a BrainByte signup that unlocks the rest, plus a "Cover the right answers" study toggle; lesson markup in `_includes/bb-lesson.njk`). The gate is an **email-code sign-up** (after charliehills.ai): the reader enters an email, `netlify/functions/guide-otp.mjs` (`/api/guide-otp`) emails a 6-digit code via Resend (`RESEND_API_KEY`, `RESEND_FROM`), and a correct code subscribes the address to Substack from the server and sets two cookies: an HttpOnly signed `bb_unlocked` (HMAC with `OTP_SECRET`) and a readable `bb_verified=1`. `src/assets/guides.js` opens the lessons when `bb_verified` is present (one sign-up opens every guide). Verified emails are kept as SHA-256 hashes in the `guide-subscribers` Netlify Blobs store, so a returning reader gets "Welcome back", still confirms with a code and isn't subscribed twice; codes are in the `guide-otp` store (10 minutes, 5 tries, 45 s between sends, 5 an hour). Substack's bot protection refuses the server-side sign-up from Netlify (403), so the page then posts the same Substack form from the reader's browser into a hidden iframe (CSP `frame-src` allows `https://*.substack.com`); no new tab or extra click. If the code service can't be reached it falls back to the old soft gate (form posts to Substack in a new tab, page opens). The lessons stay in the HTML (SEO, no-JS readers); the **PDFs** are enforced: `domain-router.js` sends any `/files/{slug}-study-guide-edition-N.pdf` request without a valid `bb_unlocked` to `/guides/{slug}/#unlock` (keep that PDF naming; until `OTP_SECRET` is set PDFs stay open). Under `netlify dev` without `RESEND_API_KEY` the code is shown on the page and logged, and nothing goes to Substack unless `GUIDE_OTP_SUBSTACK=1`. Free resources (`/resources/`) are never gated. PDFs live in `src/files/` (passthrough, served at `/files/{name}` on the apex); a new edition gets a new filename. A guide's `track` hides the matching coming-soon track. Claude/Certification posts end with a CTA to `/guides/` (`article.njk`). Locally (`eleventy --serve`) browse `http://localhost:8080/guides/`; the hub is at `/home/`.

Both domains (plus the old brainbyte one, now only redirecting) are attached as custom domains on the **same** Netlify site — this is one build, routed by hostname, not two separate deployments.

Because of this split, cross-links between the two surfaces are **absolute, cross-domain URLs**, not relative paths — relative links only work for same-domain navigation. Both domains live in `src/_data/site.json` (`url` = blog subdomain, `portfolioUrl` = apex domain) and every template references those, never a literal domain string: `src/index.html` (portfolio) links to blog posts/`/ask/`/blog home via `{{ site.url }}...`, while `base.njk`/`article.njk`/`src/blog/index.njk` (blog surfaces) link to the portfolio via `{{ site.portfolioUrl }}`, and `sitemap.njk`'s portfolio entry does the same. There's no shared nav partial, so adding a new cross-surface link means using the right `site.*` variable in whichever template needs it. The one exception is `netlify/edge-functions/domain-router.js` — it runs on Netlify's separate Deno edge pipeline and can't import `site.json`, so its hostname constants are kept in sync with `site.json` by hand (comment in the file notes this).

### Two separate layouts (do not assume they share CSS)

- `src/_includes/article.njk` — standalone layout for individual blog **posts**. Has its own `<style>:root{}` block (Source Serif 4 article font). Mermaid.js is loaded here from a CDN, so ```` ```mermaid ```` fenced blocks in posts render as diagrams.
- `src/_includes/base.njk` — layout for **non-post** pages (`/now/`, `/ask/`, tag pages).

Each (plus the standalone `src/blog/index.njk`) has its own inline design tokens, but all three then load **`src/assets/site-theme.css` last**, which overrides those tokens, fonts (Lato for interface text) and the nav so the blog matches the portfolio and the hub. To change the site-wide look of the blog, edit `site-theme.css`; to change one layout's structure, edit that layout. Post bodies deliberately keep the Medium-style serif reading column (`--font-article`, Source Serif 4). The blog is the **marketing surface**: promos use the `.promo-*` classes in `site-theme.css`.

**Colour rule (all surfaces):** one accent family, Apple-style blue, on white / neutral greys (modelled on charliehills.ai). `--pop` #0071E3 is for solid fills (buttons, badges, the logo mark) always with white text; `--brand`/`--link` are #0066CC on light and #2997FF on dark; `--brand-soft` (#E8F1FD) is the light tint for chips and card backgrounds. The tokens are defined in `portfolio.css` (hub, CV, guides; plus the light reading tokens in `guides.css`) and `site-theme.css` (blog surfaces); the layouts' own inline `--pop` defaults match. The AskHari.ai bubble uses the same blue (`--ah-accent` in `ask-hari-widget.css`). Highlighted headline words on the apex use `.pf-glow` (flat #2997FF, no gradient or glow). Don't add a second accent hue for text or UI (earlier amber, navy and lime versions were dropped); the only other colours are the hub's glossy `.ico3d` icon tiles (a small fixed palette: blue, violet, green, amber, slate), the fixed brand colours of logos/social icons, Claude's orange on the practice packs, and the warm gold light of the comets and gold stars in the canvas night sky (a light effect only, never used for UI). The apex pages use the Apple system font stack with Inter as fallback (`--font`, `--font-display`, weight 600 headings); the blog still uses Lato.

### Post assets and the `.eleventyignore` interplay

Per-post diagrams live in `src/images/posts/{post-slug}/` — SVGs/PNGs (`<img>` in a `<figure>`) and **interactive HTML diagrams** (embedded via `<iframe>`). Critical setup:

- `.eleventyignore` contains `src/images/**` so Eleventy does **not** treat those HTML files as templates to render.
- `addPassthroughCopy("src/images")` in `.eleventy.js` still copies them verbatim to `_site/`.
- iframe HTML renders without the parent page's CSS, so any CSS variables it uses must be defined in its own `<style>:root{}` block.

Don't hand-write the `<figure>`/`<img>`/`<iframe>` markup in post content — use the `figure` and `diagram` Eleventy shortcodes (defined in `.eleventy.js`, work inside post markdown because `markdownTemplateEngine: "njk"` runs Nunjucks over the content before markdown-it parses it):

```
{% figure "diagram.png", "Alt text", "Caption shown under the image" %}
{% diagram "diagram.html", "Diagram title", "Caption shown under the diagram" %}
{% diagram "diagram.html", "Diagram title", "Caption", 600 %}
```

For video, `{% youtube "VIDEO_ID", "Title", "Optional caption" %}` embeds a responsive 16:9 player from `youtube-nocookie.com` (allowed in the CSP `frame-src`). Set `site.youtubeUrl` in `site.json` to show a YouTube link in the blog sidebar.

The `figure` and `diagram` shortcodes default to resolving the file against `src/images/posts/{fileSlug}/`. A handful of older posts (e.g. `building-enterprise-data-platform-lessons-learned.md`) have an asset folder name that doesn't match the post's fileSlug — pass an explicit folder as the last argument (`{% figure "...", "...", "...", "other-folder" %}` / `{% diagram "...", "...", "...", 440, "other-folder" %}`) in that case.

### Caching (matters when post diagrams look stale)

`netlify.toml` sets `/images/*` to long cache (30 days) but `/images/posts/*` to `max-age=0, must-revalidate` so diagram/iframe updates propagate. The CSP there allows `cdn.jsdelivr.net` (Mermaid) and `cdn-images-1.medium.com` (images), and `frame-src 'self'` for same-origin diagram iframes. Changing diagram embedding or adding a CDN means updating this CSP.

### Redirects

`netlify.toml` redirects old `.html` blog URLs and the legacy Medium-article slug to current `/blog/{slug}/` paths. Add a redirect there when renaming a post slug.

### AskHari.ai (chat assistant)

A site-wide chat widget answering recruiter questions about Hari's background and reader questions about the article they're on:

- `src/_data/profile.json` — the assistant's sole source of truth about Hari (certifications, skills, experience, clients, offerings). The portfolio page renders from it too, so editing it updates both.
- `netlify/functions/ask-hari.js` — the backend. Calls the Anthropic Messages API first (`ANTHROPIC_API_KEY`); on any failure or missing key, falls back to OpenRouter (`OPENROUTER_API_KEY`) so the widget stays functional on a free/open-source model. `netlify.toml` proxies `/api/ask-hari` → this function so the browser never sees the `/.netlify/functions/` path.
- `src/assets/ask-hari-widget.{css,js}` — the one shared widget UI (passthrough-copied via `.eleventy.js`), included with two `<link>`/`<script>` tags near `</body>` in all three of `base.njk`, `article.njk`, and `src/index.html` — the only intentional exception to "no shared partial" in this repo, since the alternative was tripling the widget markup.
- On article pages the widget auto-detects `.article-body`/`.article-title` in the DOM and sends that article's text as context, so it can answer questions about the specific post being read as well as about Hari's profile.
- Both API keys are read from env vars only, never hardcoded — see `.env.example`.
